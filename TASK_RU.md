# Задача: разбор status report

**Время: 60 минут.** Синтаксис и документацию смотреть можно и нужно — гуглить, открывать доки, подглядывать в примеры. Нельзя только одно: отдать задачу целиком чат-боту и списать ответ.

## Контекст

AviaTX ведёт техобслуживание самолётов. Status report — основная выгрузка по борту: список задач техобслуживания (тасков), когда каждая выполнялась последний раз и когда должна быть выполнена снова.

Такие файлы регулярно приходят от заказчиков и из смежных систем. Данные в них грязные: формат менялся, часть значений вбивали руками, часть выгружали из старых систем. Ваша задача — превратить такой файл в строгий JSON, которым уже можно кормить код.

## Что нужно сдать

Дописанный `parse.py`, запушенный в ваш форк. Проверки прогонятся сами —
в GitHub Actions и локально одной и той же командой:

```bash
python parse.py data/status_report.xlsx > result.json
python validate.py result.json     # структура ответа
python selfcheck.py result.json    # сверка значений
```

`selfcheck.py` сверяет ваш ответ с эталоном по хешам: он скажет, какая колонка
и в каких строках разошлась, но не покажет ожидаемого значения.

`parse.py` уже лежит в репозитории как **заготовка**: в нём готовы разбор аргумента,
сборка итогового объекта, все сортировки и вывод. Дописать нужно одну функцию —
`parse_workbook()`, она читает файл и возвращает четыре вещи: борт, список
записей, список дефектов и список повторяющихся кодов. Остальное можно не трогать.

Библиотеки на ваш выбор (`openpyxl`, `pandas` — что удобнее).
Ориентир по объёму: рабочее решение — это примерно 130 строк кода.
Если получается сильно больше, скорее всего вы усложняете.

## Колонки файла

| Колонка | Смысл |
|---|---|
| `TASK CODE` | Код таска |
| `TASK TYPE` | Тип: COM (компонент), SER (регламентная работа), AD, SBI, PKG |
| `ATA` | Номер главы ATA |
| `DESCRIPTION` | Описание |
| `PART #`, `SERIAL #` | Номер и серийник установленного компонента |
| `CW MOS` | Дата последнего выполнения (C/W — compliance/work) |
| `CW HRS` | Наработка борта на момент выполнения, в формате **ЧЧ:ММ** |
| `CW CYCL` | Циклы (посадки) борта на момент выполнения |
| `Next Due MOS` | Дата следующего выполнения |
| `PRIMARY` | Код главного таска, к которому привязан этот |
| `RELATED` | Коды связанных тасков; **несколько кодов в ячейке разделены переводом строки** |

`DESCRIPTION`, `PART #` и `SERIAL #` в итоговый JSON не идут.

## Итоговый JSON

Один объект вот такой формы. Числа в верхней части **выдуманы** — они показывают только вид; две записи в `tasks` настоящие, это первые две строки листа:

```json
{
  "aircraft": "RA-00001",
  "tasks_total": 100,
  "duplicate_codes": ["AAA-111-22", "BBB-333"],
  "hours_by_type": { "AD": 1234.5, "COM": 2345.67, "SER": 34567.8 },
  "errors": [
    { "row": 57, "column": "CW HRS", "kind": "invalid_minutes", "raw": "7:88" }
  ],
  "tasks": [
    {
      "row": 3,
      "code": "339029-708",
      "type": "COM",
      "cw_date": "2010-01-26",
      "cw_date_note": null,
      "cw_hours": 50.2,
      "cw_cycles": 18,
      "next_due_date": "2016-01-26",
      "next_due_is_manual": false,
      "next_due_is_frozen": false,
      "primary_row": null,
      "related_rows": []
    },
    {
      "row": 4,
      "code": "52-11-25-101",
      "type": "SER",
      "cw_date": "2023-11-27",
      "cw_date_note": null,
      "cw_hours": 4661.85,
      "cw_cycles": 1664,
      "next_due_date": "2024-05-27",
      "next_due_is_manual": false,
      "next_due_is_frozen": false,
      "primary_row": null,
      "related_rows": [19, 48]
    }
  ]
}
```

### Поля верхнего уровня

| Поле | Тип | Что положить |
|---|---|---|
| `aircraft` | строка | Регистрационный номер борта. Он есть на листе. |
| `tasks_total` | целое | Сколько записей получилось в `tasks`. Считает заготовка. |
| `duplicate_codes` | список строк | Коды тасков, которые встречаются на листе больше одного раза. |
| `hours_by_type` | объект | Сумма `cw_hours` по каждому `TASK TYPE`. Считает заготовка. |
| `errors` | список объектов | Дефекты данных, см. следующий раздел. |
| `tasks` | список объектов | По одной записи на каждую строку данных, в порядке строк листа. |

Сортировки (`duplicate_codes`, ключи `hours_by_type`, `errors`) делает заготовка — думать о них не нужно.

### Поля записи в `tasks`

| Поле | Тип | Что положить |
|---|---|---|
| `row` | целое | Номер строки в Excel — тот, что показывает сам Excel слева (нумерация с единицы). |
| `code` | строка | `TASK CODE` |
| `type` | строка | `TASK TYPE` |
| `cw_date` | `"ГГГГ-ММ-ДД"` или `null` | Дата из `CW MOS`. Если в ячейке не дата — `null`. |
| `cw_date_note` | `"EFF"`, `"EBT"`, `"NA"` или `null` | Заполняется, когда в `CW MOS` вместо даты стоит пометка. Какая пометка какому значению соответствует — видно по самой ячейке. |
| `cw_hours` | число или `null` | `CW HRS` в десятичных часах, 2 знака после запятой. Это часы и минуты, а не дробь: `"50:12"` → `50.2`, `"4661:51"` → `4661.85`. |
| `cw_cycles` | целое или `null` | `CW CYCL` |
| `next_due_date` | `"ГГГГ-ММ-ДД"` или `null` | Дата из `Next Due MOS`. |
| `next_due_is_manual` | `true` / `false` | Дату проставили вручную. В ячейке для этого есть признак — найдите его. |
| `next_due_is_frozen` | `true` / `false` | Дату сдвинули из-за заморозки. Признак тоже в ячейке. |
| `primary_row` | целое или `null` | **Номер строки** таска, на который ссылается `PRIMARY`. Код из ячейки надо найти среди строк листа и заменить на её `row`. Пусто в ячейке — `null`. |
| `related_rows` | список целых | Номера строк для кодов из `RELATED`, в порядке ячейки. Коды, попавшие в `errors`, в список не идут. Нет кодов — пустой список. |

Пустая ячейка → `null`; там, где ожидается список, — пустой список. Лишних полей быть не должно: `validate.py` на них ругается.

### Ссылки между тасками

`PRIMARY` и `RELATED` содержат **коды**, а в JSON нужны **номера строк**. То есть код из ячейки надо найти среди строк листа и подставить `row` найденной записи.

Разрешить ссылку получается не всегда. Действует одно правило:

> **Если ссылка попала в `errors` — в результат она не идёт вовсе.**

Какой номер строки там «на самом деле» — вопрос спорный, и полагаться на него нельзя. Для `related_rows` это значит, что проблемный код просто не даёт элемента: в списке остаются только разрешённые ссылки, и он может оказаться короче, чем кодов в ячейке, или пустым. Для `primary_row` остаётся `null`.

## Дефекты данных

В файле есть ячейки с испорченными данными. Их нужно **и починить, где это возможно, и зафиксировать** в массиве `errors`. Каждая запись — объект из четырёх полей: `row`, `column` (заголовок колонки), `kind` и `raw`.

Допустимые значения `kind` — ровно эти пять:

- `invalid_minutes` — значение в `CW HRS` не может быть корректным временем. Такие записи получают `cw_hours: null`.
- `number_as_text` — число в `CW CYCL` сохранено как текст. Значение нужно восстановить в `cw_cycles` как целое число, а факт — записать в `errors`.
- `self_reference` — таск ссылается сам на себя в `RELATED`.
- `ambiguous_reference` — ссылка не разрешается однозначно: такой код встречается на листе больше одного раза.
- `unknown_reference` — ссылка ведёт в никуда: такого кода на листе нет вообще.

В `raw` кладите **то, к чему претензия**, без очистки:

- `invalid_minutes`, `number_as_text` — содержимое ячейки целиком;
- `self_reference`, `ambiguous_reference`, `unknown_reference` — тот самый код, а не всю ячейку: в `RELATED` кодов может быть несколько, и проблемный из них — не обязательно единственный.

## На что обратить внимание

Файл не стерильный. В нём есть значения, которые не укладываются в описание колонок выше, — они тоже должны корректно доехать до JSON, поля для этого есть. Прежде чем писать парсер, потратьте несколько минут на то, чтобы **посмотреть на данные**: автофильтром в Excel, сортировкой, кодом — чем угодно.

Если какое-то место осталось непонятным — спросите вслух, это нормально и не штрафуется.
